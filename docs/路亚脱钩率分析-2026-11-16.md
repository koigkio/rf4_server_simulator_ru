## 一、f0=1 掷骰输入完全钉死（原 §七欠账清偿）

kldglnchdec ctor（il2csharp_full/Assembly-CSharp/kldglnchdec.cs:54-113，全文无剥离）：

```
v = 鱼种拉力 jfhcjbbkalp()                       ← 静态种值，服务端下发（已证无运行时写入者）
if 钩组件 annldpcofdn != null 且 钩件总数 > 0:
    v = v × (挂鱼钩数 kcgjlnmdbol() / 钩件总数 pjkhmifjcng())   ← C# 整除
    if 满足谓词组合: v *= 0.05
if !mkkielhmcgn(v):                                  ← v<1e-45 必死 / v≥1 必活 / 否则死率 1−v
    装填 Random(0.5,2.0)s 计时器 → 到点 f0=1 必死
```

两个计数器的语义（共用体剥离，靠两处独立调用点消歧）：

| 函数 | 语义 | 证据 |
|---|---|---|
| `pjkhmifjcng()` | **钩件总数**（钩槽数组 `gpoaffnjbdo.Length`） | LureComplex.cs:1818 与 knmjphiefdm.cs:469 都遍历 `pbfnolmjemp(0..n)` 渲染每枚钩模型 |
| `kcgjlnmdbol()` | **当前挂鱼的钩数** | LureComplex.ddbonhjijbn:1788：`>0` 时把已挂鱼模型摆到 hook_point |

**关键算术**：单钩 Wacky 的比值只能是 0 或 1（整除）。
- 比值=1 → v=拉力 ≥1 → **必活**；
- 组件 null 或钩件数=0 → 比值块跳过 → v=拉力 → **必活**（公式对"坏状态"全部宽容）；
- 挂鱼钩数=0 且钩件数>0 → v=0 → **必死**。

351N 的 nelma 也死在 f0=1（×0.05 路径杀不死 ≥2N 的鱼：351×0.05=17.6≥1）⇒
**每一例大鱼死亡都必须走"挂鱼钩数=0"这条唯一致死路径**。20~30% 的死亡率 = 进场 ctor
瞬间客户端"挂鱼钩数=0"状态的出现频率，不是连续概率参数偏小。

## 二、服务端 wire 洁净性（排除服务端数据字段）

- 死/活两组鱼的 14/1、14/2、800 回复装备树、4/22 帧内容**逐字节无差**（p422_race_check.py v2，15 尾死鱼全同构）；
- 14/11 是客户端→服务端：客户端掷骰 ctor 在**发出 14/11 之前**执行，服务端 +0.01s 的
  4/22 推送结构上不可能影响本尾掷骰；
- 拉力 = 静态种值（gkfghccolil offset 0x88），XOR 对抗篡改对，**无运行时写入者**；
- 4/22 钩帧 141B 裸钩 vs 官方 429B 拟饵容器：官方容器形仅限"钩行归属拟饵"（内嵌双钩的假饵），
  Wacky 钩是独立 rig 行，裸钩+挂载位合规（lure-fight-mount-flags spec 行 58/106）。

**结论：不存在任何一个服务端装备树字段，改了能改变这个掷骰。**
原方案"钉死输入→对着改装备树字段"的前提被证伪：比值分子/分母都是客户端运行时状态，

## 四、机制收敛：咬饵≠咬钩（客户端两阶段模型）

2026-11-16 晚复核客户端字节码，模型从「单次掷骰」修正为**两阶段**：

**阶段一：进场保持检查（kldglnchdec，14/11 时刻一次性）**
- 掷骰 v = 鱼拉力 × (挂鱼钩/钩件 整除) × {1|0.05}（§一公式）；
- **通过** → 鱼真正挂住，客户端此时才调度「上鱼」通知
  （gfgapohfogm：通知只在 `!ofiaigpneom`，即掷骰通过时挂）；
- **失败** → 鱼叼住拟饵 0.5~2.0s → 吐出 → **f0=1**。全程无「上鱼」提示、无真实搏鱼。

**阶段二：搏鱼期脱钩危险（kejihbadeej，搏鱼中逐帧累计）**
- 危险率按鱼体力比、搏鱼时长平滑衰减（60s→3600s 降到 1/80）、泄力开度
  （0.3~1）、冲刺态调制，周期掷骰 → 失败 = **f0=2 真脱钩**。

当天数据逐类吻合：f0=1+hooked ×21 全部 gap 0.57~1.86s、负载帧全 1 条、
含 **18.9kg/1.45s**（不存在「1.45 秒跑掉 18.9 公斤」，只存在咬一口没钩住）；
f0=2+hooked ×7 中 21.4s/11 帧、42.0s/22 帧为真搏鱼脱钩。客户端本地化
模板表只有 4/5/6/7/10/30（轮坏/竿坏/主线断/脱钩/牙咬断/子线断），
**无「没钩住/吐饵」类载体** → 官方对阶段一失败完全静默。

## 五、已落地：播报节点对齐官方（2026-11-16 实装）

- `handlers_game.go` 14/12 已中鱼分支按 f0 分流：**f0=1 → 静默**（不播报、
  不计 escapes、不触发大鱼脱钩补偿）；**f0=2/8 → 真脱钩**播报 + 计数 + 补偿。
  磨损结算、同竿重排、多钩接管不变；未知 f0 兜底分支保持保守播报。
- `progress_ops.go` 14/4 收竿未刺中补报取消（同属咬饵未咬钩，官方静默）。
- 17/9 断件（断线/断竿/轮坏/牙咬断/子线断）保留——官方模板 4/5/6/10/30 真实存在。

效果：下午段跑鱼播报 21 → ~7 条（≈中鱼的 6%），全部为真实搏鱼脱钩；
escapes 统计与巨物补偿不再被未挂牢的鱼污染。

残留未知：阶段一失败率（当天该竿 21~25%）官服同场景取值离线不可证；
但语义修正后与速率无关——叼住吐出无论如何不该有播报载体。
逃鱼后的传染梯度（21%→36%→58%，§三）仍为客户端/调度侧持续态，是独立课题。

## 六、结论（TL;DR）

> 「路亚脱钩率为什么高」实为两个叠加现象：客户端阶段一「叼住吐出」
> （f0=1，咬饵未咬钩，官方本就静默）被我们按真脱钩播报，制造了
> 「跑鱼极多」的体感；真正的阶段二脱钩（f0=2）只占中鱼的 ~6%。
> 已按官方语义把 f0=1 改为静默（连同收竿未刺中），播报、escapes 计数、
> 巨物补偿只认真脱钩。
